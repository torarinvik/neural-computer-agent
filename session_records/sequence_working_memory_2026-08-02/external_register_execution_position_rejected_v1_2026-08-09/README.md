# Normalized execution position — rejected

The shared external interpreter was given an optional generic normalized
sinusoidal program-counter signal. The signal is structural only: it carries
step position and normalized program length, not operation names, task IDs, or
protocol metadata.

The sub-minute screen was undertrained and was not used for a decision. At the
matched full budget on seed `69316`, primitive retention was strong (`0.8828`)
and persistence, frozen-parent, missing-evidence, and reward-shuffled controls
passed. The inherited four-instruction composition nevertheless finished at
`0.7148` and never reached a stable prefix, while the matched fresh learner
reached stable mastery at `16,384` verifier bits. The existing no-position
baseline reaches `0.8477` composition accuracy and a `28,672`-bit stable prefix
on the same rung.

Decision: reject normalized execution position as a current capability or
transfer accelerator and remove it from the production branch. The result
does not disprove a program counter as a long-term machine primitive; it shows
that adding position to the existing register code does not repair the
portable serial algebra. The next intervention must address execution state
and representation, not another code-side conditioning feature.
